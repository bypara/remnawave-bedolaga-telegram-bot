# Режим переезда бота

По умолчанию выключен. Это заглушка входящих действий, а не переключатель
инфраструктуры: домены, база, платежи и фоновые задачи не меняются.

В админке бота: «Настройки бота» → группа обслуживания → категория
«🚚 Переезд бота». В кабинете — та же категория системных настроек.

1. Задать `BOT_MIGRATION_URL`: `https://t.me/new_service_bot` или ссылку
   с `?start=campaign_code`. Новый бот уже должен работать.
2. Задать `BOT_MIGRATION_MESSAGE` (обычный текст, не HTML/Markdown) и
   `BOT_MIGRATION_BUTTON_TEXT`.
3. Включить `BOT_MIGRATION_ENABLED`. Действует сразу, без перезапуска.
4. Для отмены выключить `BOT_MIGRATION_ENABLED`.

Настройки сохраняются в `system_settings`. Миграция 0132 добавляет таблицу
персональных ссылок/начислений `bot_migration_claims`; применяется при обновлении
бота. Переменные `.env` с такими же именами имеют приоритет над админкой.

## Бонус за переход

1. Задать `BOT_MIGRATION_BONUS_AMOUNT_RUBLES` в рублях (например `75.50`).
2. Включить `BOT_MIGRATION_BONUS_ENABLED`.
3. В текстах `BOT_MIGRATION_MESSAGE`, `BOT_MIGRATION_BUTTON_TEXT` и
   `BOT_MIGRATION_BONUS_SUCCESS_MESSAGE` можно использовать `{bonus}`.
   Например: «Перейти и получить {bonus} ₽».

Старый бот выдаёт персональный `?start=move_...` зарегистрированному активному
пользователю. Он заменяет рекламный start-код из настроенного URL. Сам клик
не виден боту: деньги начисляются после `/start` в новом боте по этой ссылке.
Оба бота должны использовать одну БД и эту версию кода.

Токен связан с аккаунтом; пересылка ссылки не даёт бонус другому человеку.
Начисление, история с методом `manual` и отметка получения сохраняются одной
транзакцией. Повторный запуск, смена суммы и переключение режима не дают бонус
повторно. Кампании и реферер пользователя не изменяются.

Уже выданная ссылка сохраняет обещанную сумму. Новая сумма действует для
пользователей, которым ссылка ещё не выдавалась. Изменение целевого бота
перевыпускает невостребованную ссылку при следующем обращении к старому боту.
Старый токен перестаёт работать; уже начисленный бонус не сбрасывается.

Для уже получивших бонус и не подходящих аккаунтов используются изменяемые
`BOT_MIGRATION_NO_BONUS_MESSAGE` и `BOT_MIGRATION_NO_BONUS_BUTTON_TEXT`.
При отключённом бонусе работает обычная настроенная ссылка.

## Что перехватывается

- Личные сообщения, команды, `/start` с любым payload.
- Callback-кнопки, включая старые/неизвестные и кнопки в inline-сообщениях.
- Активные пользовательские FSM-диалоги: их обработчики не вызываются.

Администраторы из `ADMIN_IDS` сохраняют обычный доступ. Сообщения в группах
не заменяются заглушкой. URL/WebApp-кнопки уже отправленных сообщений открываются
самим Telegram и не могут быть перехвачены middleware.

Бот, чьё подтверждённое Telegram-имя совпадает с именем из целевой ссылки,
не показывает заглушку: новый бот остаётся рабочим даже с общими настройками БД.
На нём сохраняются обычные проверки доступа и обязательных каналов. При проходе
канальной проверки код переезда хранится отдельно от рекламной атрибуции в FSM.

`successful_payment` и `pre_checkout_query` не перехватываются режимом переезда.
Внешние платёжные вебхуки тоже продолжают работать. Старые счета нужно учитывать
при переключении полноценного сервиса на нового бота.

## Важно для будущего переезда

- Ссылки рекламных кампаний не используются для бонуса переезда: у него отдельный
  персональный сценарий для существующих пользователей.
- Не запускайте два полноценных сервиса с автопродлением/мониторингом на одной БД.
  После переноса старому боту нужен отдельный лёгкий процесс-заглушка без фоновых
  задач: `python -m app.migration_bot` (описание ниже). Флаг переезда сам по себе
  не выключает задачи в обычном `main.py`: новый бот должен продолжать их выполнять.
- Старые ссылки на подарки/рефералов не пересылают payload автоматически: сейчас
  кнопка использует ссылку перехода/персональный код переезда. Для их сохранения нужен отдельный
  сценарий совместимости перед реальным переключением.
- Кабинет можно перенаправлять `app.huntcdn.com` → `web.censet.net`, сохранив путь
  и query string. Не применяйте общий редирект к API/платёжным webhook-маршрутам.
  Подписочный домен лучше сохранить как работающий совместимый адрес.

## Новые домены

- `web.censet.net` — кабинет (включая same-origin `/api`).
- `sub.censet.net` — подписочные ссылки, без смены ключей/путей пользователей.
- `hooks.censet.net` — Telegram, RemnaWave и платёжные вебхуки.
- `censet.net`/`www.censet.net` — необязательны, для сайта/страницы перехода.

Отдельный `api.censet.net` текущей архитектуре не нужен. Панель RemnaWave может
остаться на прежнем служебном домене. Старые домены `app/sub/hooks.huntcdn.com`
сохраняются для совместимости; общим редиректом вебхуки не закрываются.

## Отдельный лёгкий запуск старого бота

Обычный запуск `python main.py` не изменён. Оба контейнера используют один
проверенный образ, но старый запускается командой `python -m app.migration_bot`.
Это отдельная точка входа: нет `setup_bot`, обычного меню, кабинета, платежных
HTTP-маршрутов, миграций/создания БД, списаний, мониторинга, синхронизации, бэкапов
и других бизнес-планировщиков. Есть только Telegram-транспорт, `/health`,
заглушка и обработчики завершения ранее выставленных Stars-счетов.

Запуск требует включённого `BOT_MIGRATION_ENABLED`, ссылки на нового бота,
токена **старого** бота (имя сверяется через Telegram) и уже обновлённой общей БД.
Выключенный переезд или токен целевого бота приводят к отказу запуска **до**
изменения Telegram webhook. Никакого автоматического перехода в полноценный
режим нет. Если флаг выключен во время работы, старый бот показывает сообщение
«Переезд временно приостановлен»; фоновые задачи не появляются. Старые оплаченные
Stars-события и pre-checkout по-прежнему направляются в обработчики платежей.

Настройки читаются из общей БД при каждом update, с прежним приоритетом `.env`.
Загрузка в этом процессе не вызывает обычные apply-hook-и настроек, которые
могут запускать бэкапы/синхронизацию. Администраторы в старой заглушке также видят
переход; админка остаётся в новом полноценном боте/кабинете. FSM — отдельная
MemoryStorage: не затрагивает Redis-состояния нового бота. Старые подсказки
оплаты из FSM могут не удалиться, но начисление определяется платёжным payload.

Пример Compose — дополнительный `docker-compose.migration.yml`, который сам
ничего не переключает и имеет профиль `migration`. Секретный `.env.migration`
создаётся оператором на сервере и **не коммитится**. Общий `.env` — нового
полноценного сервиса; `.env.migration` переопределяет только старую идентичность
и транспорт. Пример без реальных секретов:

```dotenv
BOT_TOKEN=<токен старого бота>
BOT_USERNAME=<имя старого бота без @>
BOT_RUN_MODE=webhook
WEBHOOK_URL=https://hooks.huntcdn.com
WEBHOOK_PATH=/webhook
WEBHOOK_SECRET_TOKEN=<отдельный секрет старого webhook>
```

Не закрепляйте изменяемые `BOT_MIGRATION_*` в `.env`, если хотите управлять ими
из админки. Укажите `BOT_MIGRATION_IMAGE` — тот же проверенный образ, что у
основного сервиса. Проверка конфигурации и **явный** запуск (не выполнять,
пока не подготовлен полноценный новый бот):

```sh
docker compose -f docker-compose.yml -f docker-compose.migration.yml --profile migration config --quiet
docker compose -f docker-compose.yml -f docker-compose.migration.yml --profile migration up -d --no-deps migration-bot
```

В overlay нет опубликованных портов: reverse proxy должен направить отдельный
маршрут/домен старого Telegram webhook на `migration-bot:8080`. Полноценный бот
использует **другой** маршрут/домен. Для webhook обязателен отдельный секрет;
запросы обрабатываются до HTTP-ответа, pending updates не сбрасываются. Можно
вместо webhook задать `BOT_RUN_MODE=polling`: старый webhook будет снят без
сброса очереди, маршрутизация reverse proxy для заглушки не потребуется.

Перед переключением остановите прежний полноценный процесс старого бота.
Только новый сервис должен выполнять бизнес-задачи. У старого бот-токена должен
быть ровно один потребитель updates. Смена токена не переносит пользователей
Telegram автоматически: новый бот сможет отправлять им сообщения после `/start`.

Внешние платёжные и RemnaWave webhooks — не Telegram updates. Их старые URL
нужно сохранить и направлять в полноценный backend; **не** в лёгкую заглушку
и **не** под общий редирект. Перед реальным переключением отдельно проверьте
старые счета, провайдерские подписи/секреты, авторизацию кабинета и сохранение
`CABINET_JWT_SECRET` (смена `BOT_TOKEN` не должна менять ключ JWT).

## Рассылки из кабинета от старого бота

В форме рассылки можно выбрать «Основной бот» или «Старый бот» и независимо
добавить кнопку перехода в нового бота. Для старого отправителя задайте
`LEGACY_BOT_TOKEN` в секретном окружении полноценного backend. При отсутствии
токена старый отправитель недоступен: подмены основным ботом нет.

Это только исходящие Telegram-запросы: второй consumer, webhook и фоновые
бизнес-задачи не запускаются. `BOT_MIGRATION_ENABLED` не переключается и не
обязателен для рассылки. Ссылка и тексты кнопки берутся из настроек переезда.
При включённом бонусе подходящим пользователям выдаётся персональная ссылка
с однократным начислением после `/start` в новом боте; остальным — обычная
ссылка без обещания бонуса. Сумма и тексты настраиваются там же.

Вложение загружается выбранным ботом, поскольку Telegram file_id привязан к
его токену. Для смены отправителя удалите вложение и загрузите заново.
Отправитель и наличие кнопки сохраняются в истории рассылки (миграция БД 0133).
Перед отправкой есть предпросмотр и явное подтверждение; сама настройка формы
ничего не рассылает. Новый бот должен быть подготовлен до публикации ссылки.
