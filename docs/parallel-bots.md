# Приватное тестирование второго бота

Пока старый бот остаётся полноценным, второй можно запускать только через
`python -m app.interactive_bot`, не через второй `main.py`.

## Разделение ролей

- `BOT_PROCESS_ROLE=primary` — прежний полноценный backend: кабинет, внешние
  платёжные/RemnaWave webhook-и, списания, уведомления, синхронизация, очереди,
  бекапы и остальные периодические задачи. Значение по умолчанию: существующее
  одиночное развёртывание не меняется.
- `BOT_PROCESS_ROLE=interactive` — отдельный приватный Telegram-транспорт с
  пользовательскими обработчиками и общей БД. Не делает миграции, bootstrap,
  массовые рассылки, синхронизации или запуск фоновых бизнес-сервисов. Админские
  Telegram-обработчики не регистрируются; управление остаётся в primary/кабинете.

Это не распределённый планировщик: должен быть **ровно один primary-процесс**.
Роль защищена от редактирования через общие настройки. `main.py` отказывается
работать с интерактивной ролью. Настройки второму боту читаются без apply-hook-ов,
которые запускают автосинхронизацию и бекапы.

## Безопасность тестового запуска

Нужны общие PostgreSQL и Redis, уже актуальная схема БД, ожидаемое имя второго
бота, числовой ID текущего primary-бота и непустой список Telegram ID тестеров.
Токен primary-бота отвергается до изменения webhook; несовпадение username и
неактуальная схема тоже блокируют запуск. Боты не должны использовать один токен.

Redis FSM второго бота имеет отдельный префикс и bot_id; прежние ключи primary
не меняются. Redis lease запрещает два интерактивных consumer одного токена;
при потере блокировки интерактивный процесс завершается. Это служебная задача
транспорта, не дополнительный бизнес-планировщик.

Пользователи вне allowlist видят только сообщение о тестовом режиме. Их
pre-checkout отклоняется. Уже завершённые Stars-платежи передаются обычным
обработчикам даже после удаления тестера из allowlist, чтобы не терять оплату.
Другие пользовательские действия работают с настоящей общей БД: покупки,
промокоды и тестовая подписка не становятся «сухим прогоном» автоматически.

В интерактивном процессе нет кабинета и внешних платёжных/RemnaWave endpoints.
Не перенаправляйте туда старые hook URL. Telegram webhook, если выбран, требует
отдельного маршрута и секрета; не используйте URL/секрет primary webhook.
Перезапуск не сбрасывает очередь Telegram updates.

## Подготовленные файлы — не команда переключения

Overlay `docker-compose.interactive.yml` необязателен и имеет отдельный профиль.
Он читает текущий `.env`, затем секретный `.env.new-bot` (токен/username второго
бота) и явно закрепляет интерактивную роль. По умолчанию используется polling:
отдельный домен/маршрут для тестового Telegram-транспорта не требуется.
Порты хоста не публикуются.

Для проверки конфигурации без запуска задайте в операторском окружении:

```dotenv
BOT_INTERACTIVE_IMAGE=<проверенный образ с app.interactive_bot>
BOT_PRIMARY_ID=<числовой ID текущего основного бота>
BOT_INTERACTIVE_ALLOWED_IDS=<Telegram ID тестеров через запятую>
```

```sh
docker compose -f docker-compose.yml -f docker-compose.interactive.yml --profile interactive config --quiet
```

Реальный запуск потребует отдельного решения оператора:

```sh
docker compose -f docker-compose.yml -f docker-compose.interactive.yml --profile interactive up -d --no-deps interactive-bot
```

Проверки после запуска: `/health` возвращает `role=interactive`,
`business_workers=false`, `private_test=true`; основной бот сохраняет прежние
webhook и фоновые сервисы; доступны только перечисленные тестеры. Сам запуск
не включает переезд, не создаёт рассылку и не переключает домен/авторизацию.

## Что пока не переключать

Новый бот в тестовом режиме ещё не означает переключение Telegram OIDC,
MiniApp/initData-проверки, кабинета или отправителя фоновых уведомлений.
Если глобальное меню открывает MiniApp, вход через новый токен необходимо
подготовить отдельно перед его полноценным тестированием. Внешние платежи
обрабатывает прежний primary, поэтому уведомления о них пока идут старым ботом.

Перед повышением нового бота до primary остановите его интерактивный consumer
и прежний primary; сохраните JWT-секрет и платёжные URL. Только после отдельной
проверки покупок/продлений/старых счетов запускайте новый primary, а старый бот
переводите в согласованный режим. Лёгкая заглушка `app.migration_bot` по-прежнему
требует включённого переезда; этот overlay её не запускает.
