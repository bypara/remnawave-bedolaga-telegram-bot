# Перенос общих настроек в PostgreSQL

Настройки из `.env` и Compose имеют приоритет над `system_settings`. Для перехода
на управление из БД нужно сначала сохранить текущие типизированные значения в
БД, затем удалить соответствующие переменные из всех env-файлов и явного
`environment` Compose. Пустая строка не освобождает настройку от env override.
После изменения окружения контейнеры **пересоздаются**, не просто restart.

## Порядок запуска

`main.py` проверяет роль primary, затем `preload_database_settings()` читает БД
без apply-hook-ов и только после этого импортирует интеграции и фоновые сервисы.
Это важно для singleton-сервисов, которые сохраняют токены/параметры в своём
конструкторе. Обычная инициализация и миграции остаются у единственного primary.
Для совершенно новой БД без system_settings preload пропускается; недоступная
БД или некорректные настройки не разрешают запуск с молчаливыми defaults.

Интерактивный бот уже читает настройки до импорта setup_bot; его отдельные
identity/transport параметры остаются процессными. Не запускайте primary
entrypoint второго бота ради загрузки конфигурации.

## Что остаётся в окружении

- BOT_TOKEN / LEGACY_BOT_TOKEN, ADMIN_IDS / ADMIN_EMAILS и роли/ID тестеров.
- Доступы и параметры подключения PostgreSQL/Redis, SQLite path, размеры пула.
- JWT, bootstrap/HMAC ключи web API, секрет Telegram webhook.
- Transport/server bind параметры, URL/путь Telegram webhook, BOT_RUN_MODE.
- Различающиеся у ботов identity/OIDC параметры: они не могут одновременно
  представлять старого и нового ботов в одной общей строке system_settings.
- Нативные переменные Docker, FORCE_COLOR и TZ, не являющиеся настройками БД.

Платёжные ключи, RemnaWave API key, SMTP/Resend и общие бизнес/UI настройки могут
храниться в БД. Перед переносом следует сравнить процессные настройки обоих
контейнеров, проверить различия с существующей БД и сохранить effective config.
Для сохранения поведения записываются текущие env-значения, а не устаревшие
дубликаты из БД. Остальные, не перенесённые записи БД не изменяются.

## Проверка и безопасность

Сделайте защищённую резервную копию env/Compose и БД. Импортируйте выбранные
строки одной транзакцией без setters, запускающих schedulers. Проверьте перенос
на изолированной копии PostgreSQL и убедитесь, что холодная загрузка даёт ту же
конфигурацию и что новые интеграции действительно получают ключи из БД.
Имеющийся импорт через Telegram не является заменой этой проверке: не отправляйте
туда полный production .env с токенами/доступами.

Секреты маскируются в UI/API, но system_settings не шифрует их содержимое.
БД, дампы и миграционные payload-файлы содержат реальные секреты: ограничьте
доступ к ним и никогда не публикуйте значения в отчёте.

При откате восстанавливайте только изменённые строки настроек и env/Compose.
Не откатывайте целиком БД, если после переноса уже прошли оплаты или другие
пользовательские действия. Откат записей должен обнаруживать конкурирующие
изменения, а не затирать новые значения.

После редактирования интеграций в кабинете некоторые сервисы могут требовать
перезапуска: перенос в БД сам по себе не делает все SDK/singleton-экземпляры
автоматически перезагружаемыми.
